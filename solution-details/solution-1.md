Context ปัญหา :
เมื่อเกิดน้ำท่วมขัง ประชาชนจะส่งปัญหาไปยังระบบแนว ๆ Taffy Fondue ซึ่ง ในหลาย ๆ เคสเกิดจาก ปัญหาที่หายเองได้ (เช่น น้ำท่วมขังรอระบาย แล้ว เจ้าหน้าที่ไปลงหน้างานแล้ว น้ำไม่ท่วมขังแล้ว ก็กลายเป็นเสียเวลาและทรัพยากร) ซึ่งปัญหานี้จะเกิดภายใน Situations ของ Quick Response Unit ไม่เกี่ยวข้องกับประเด็นอื่น ๆ

Leverage Point ที่ต้องการจะปรับ (Anticipated ผลกระทบอะไรที่จะเกิดขึ้น) :
Filter ปัญหาที่หายเองได้ ออกจากปัญหาที่หายเองไม่ได้ ด้วยการทำให้ การสะสมของ False Flags หรือ False Alarm หายไป ด้วยการ Deleyed การสะสมของ Empty Case

Requirements :
a. การทำนายการลดลงของระดับน้ำ จะได้เป็น 1 Indicator ในการแยก Empty Case ที่สามารถเกิดขึ้นได้ในอนาคต
ระบบต้องสามารถคำนวณอัตราการลดลงของระดับน้ำ ผิวดินได้แบบเรียลไทม์ โดยเทียบระหว่าง ปริมาณน้ำฝนที่เหลืออยู่ กับ อัตราการระบายจริงของท่อ
หากคำนวณแล้วพบว่า เวลาที่น้ำจะลดจนแห้ง < เวลาเดินทางเฉลี่ยของ QRT หน้างาน เช่น 20–30 นาที) ระบบต้องจัดสถานะเคสนั้นเป็น "Transient / Self-Clearing" และสั่งระงับการปล่อยรถทันที หรือ Filter ออกไปเลย

b. ข้อมูลเกี่ยวกับระบบระบายน้ำในคลอง
ต้องรู้ว่ามีขยะอุดตันที่คลองมั้ย ประกอบการทำงาน
ต้องมีเซนเซอร์วัดระดับน้ำและวัดความเร็วการไหล เพื่อยืนยันว่าท่อระบายน้ำยังมีอัตราการไหลอยู่

c. Automated Dispatch Filtering Layer (ระบบ หรือ กลไกอะไรก็ตามที่สามารถกรอง Empty Case ออกได้)
เป็น Filter
ต้องการ Input ข้อมูลจากหลากหลาย sources (เช่น CCTV หรือ Local Sensors)

Constrains :
a. ข้อจำกัดทางกายภาพ เช่น ท่อระบายน้ำ และ การฝนตก
ฝนตกซ้ำ 2 รอบติดกัน เพราะ คาดเดาไม่ได้
Sensors อาจจะประเมินค่าผิดพลาด คลาดเคลื่อนจากความเป็นจริงมาก ๆ ได้จนทำให้ Verdict ผิด
b. ข้อจำกัดเชิงกระบวนการ
ทุกขั้นตอนการดำเนินงานต้องมี Evidences ส่งคืนกลับให้ประชาชน กลายเป็นว่าจะเกิดการ Forces ให้เจ้าหน้าที่ไปลงหน้างานเพื่อยืนยันสถานการณ์อีกที
Dispatch Lag ระบบราชการปัจจุบันมีขั้นตอนที่เยอะ และ ใช้เวลานานหาก Filter System ทำงานช้า หรือ ให้ข้อมูลอย่างไม่ถูกต้อง ก็จะทำให้การประเมินการใช้ทรัพยากรผิดพลาดได้

Study Case & Innovation :
เคส 1 PUB Singapores - Catchment and Waterways Operations System (CWOS)

ทำงานแบบ 2 factor Authentications

เคส 2 Ann Arbor, Michigan - Open-source Dynamic Water Network Control

ใช้ Prediction Model ผ่าน Recession Rate ของท่อระบายน้ำและบ่อพักน้ำ เพื่อแยกว่า น้ำท่วมขังเกิดจากการระบายไม่ทัน หรือเกิดจากการอุดตันถาวร เอาไว้แยก False Alarm ออกจากระบบ เพราะ Flase Alarm ที่ออกมาทั้งหมดจริง ๆ มันมาจากฝนตกหนักเกินไป


เคส 3 Acoustic Pre-Screening (UK, USA)

เก็บข้อมูลผ่าน Sensors และ Acoustic Instruments เก็บข้อมูลเป็น Mapping สภาพความสะอาดท่อก่อน จัดเทียร์เป็น 3 กลุ่ม (0-3) (4-6) (7-10)
โดยที่กลุ่ม (0-3) ต้อง Take Actions ทันที (4-6) ต้องจัดคิวทำความสะอาด (7-10) ไม่ต้องทำอะไรเลย และ ส่วนนี้จะมีผลตอน Filter Case ออกได้ เช่น มีการแจ้งเตือนมาท่วมชังบริเวรท่อที่สะอาด ก็มี chances สูงมากที่จะท่วมขังเพราะฝนตกหนัก
